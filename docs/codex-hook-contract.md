# Codex hook feasibility (documentation only)

Source: [Codex Hooks, official reference](https://developers.openai.com/codex/hooks.md), inspected 2026-09-30. This describes the documented Codex CLI hook, **not** ChatGPT's hosted tools or a tested adapter. No hook is installed by this repository.

`PreToolUse` receives JSON on stdin, including `session_id`, `cwd`, `turn_id`, `tool_name`, `tool_use_id`, and `tool_input`. A synchronous command hook may deny a supported call with `hookSpecificOutput: { hookEventName: "PreToolUse", permissionDecision: "deny", permissionDecisionReason: "..." }`, legacy `{ decision: "block", reason: "..." }`, or exit code 2 and a stderr reason. `permissionDecision: "ask"` is **not supported**: it marks the hook failed and continues the call. A policy adapter must therefore arrange a separate, verified interactive approval path and return a real deny when approval is absent or declined. Never translate portable `confirm` to `ask`, a warning, or a bare hook failure.

The documented local coverage includes shell (`Bash`), `apply_patch`, MCP tools, and most other local function tools. Hosted tools such as `WebSearch` have **no** `PreToolUse` coverage; specialized paths may opt out. A later `write_stdin` on a unified-exec session does not get a fresh `PreToolUse` check. Matching command hooks run concurrently, so another hook cannot be relied upon to serialize approval or protect a mutable input. A prototype must enumerate all reachable effect-bearing paths and explicitly exclude unsupported ones rather than claim universal enforcement.

For a Codex adapter, derive the complete execution envelope from the authenticated hook event and trusted session context; do not fabricate a user task from model arguments or copy identity from a permit. Verify actual semantics for command execution, patch application, approval UI, child processes, session restarts, concurrent hooks, and tool-input mutation. Test a real denied side effect, approved exact-input execution, changed-input rejection, decline/headless behavior, call-ID reuse, and host bypasses. Hook configuration is trust-gated for non-managed hooks and can be disabled; deployment therefore needs a verified managed or otherwise enforced installation. The current portable core intentionally has no `codex` mapping; adding one requires executable-host evidence and a separate security review.
