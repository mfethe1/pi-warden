# Portable action boundary (experimental)

`src/portable-action.ts` is a host-neutral **pre-execution policy core**, not an installed Hermes, Claude, ChatGPT, or Pi integration. Adapters must capture the actual tool invocation before execution, pass the current user's task (not agent text or retrieved content), and enforce `deny` by blocking and `confirm` by obtaining fresh, action-scoped user approval. A host that cannot intercept before execution must not claim enforcement. No approval persistence or cross-session carryover is provided here.

The core maps specific host/tool pairs: Pi (`bash`, `write`, `edit`), Hermes (`functions.terminal`, `functions.write_file`, simple `functions.patch` replace), and Claude (`Bash`, `Write`, `Edit`). These are *input-shape fixtures*, not verified hook integrations. ChatGPT has no verified hook contract and is denied until one is implemented. Cross-host tool aliases, mismatched working directories, unknown hosts/tools, unknown action-envelope fields, unexpected tool options (including background execution and timeouts), unknown nested edit fields, malformed `replace_all` values, unsupported arbitrary-code tools, bulk edits beyond the guard's sample limit, and patch-format edits fail closed rather than being guessed read-only. It never silently allows a mapped shell, write, or edit call: because shell semantics and symlink targets are not verified, even a guard `allow`/`warn` is raised to `confirm` pending action-scoped approval; an existing `deny` stays denied. This conservative default is intentionally high-friction until real host adapters and approval binding are proved. It neither connects a judge nor transmits data. The `verdict` object contains a summary and is intended for local inspection, not automatic telemetry.

## Experimental preflight seam (not wired to a host)

`preflightPortableAction` in `src/portable-preflight.ts` converts the decision into a `{ block: true, reason }` response or `{ block: false, action }` permit only after a fresh, explicit `true` from an injected approver. The policy, approver, and compliant executor must use the **same deeply frozen action snapshot returned in the permit**; the original mutable request is not authorized for execution. `executePortableAction` is an opt-in callback wrapper that passes only that approved snapshot to its executor and skips the callback for blocked requests; tool failures propagate rather than being mislabeled as pre-execution blocks. No approver, decline, approval exception, policy denial, non-JSON action, or mutation while approval is pending blocks. An in-process test proves that the wrapper skips a real local file write for declined/headless/changed requests and writes the approved snapshot despite a later original-request mutation. This does **not** prove any real host intercepts tool calls or prevents bypass of the wrapper. A host may supply a shared `PortableCallLedger` to consume `(host, sessionId, callId)` synchronously before awaiting approval; concurrent or later reuse (including after a decline) is blocked. This is opt-in, process-local replay resistance only: restarting the host resets the ledger, a new call ID is distinct, and the host must ensure session/call IDs are authentic and unique. It does not prove a reused approver callback actually solicits a fresh human decision. No durable approval token or production hook is provided. The experimental Pi binder accepts only the frozen permit object issued by this process's preflight and consumes it once: a hand-built or copied permit is rejected even if its snapshot matches. This process-local object provenance does not authenticate a human approver, survive restart, or stop arbitrary code in the process from calling preflight with its own callback. A newly approved permit remains distinct; the optional shared ledger is still needed to reject repeated call IDs at preflight. The frozen permit snapshot and successfully Pi-bound original input now detach object prototypes before execution; inherited `toJSON` cannot mask changes during comparison, and later `Object.prototype` pollution cannot supply absent optional input fields. This is a narrow plain-data guarantee, not a host integration or protection against a compromised adapter, mutable array prototypes, or unverified execution paths. Do not rely on this binder where untrusted code can mutate shared prototypes; execution must use a canonical, own-data-only action and an authenticated host call identity. The calling host must route *every relevant tool execution* through the wrapper (or enforce the block and execute the permit snapshot), before any other guard bypass. Unhooked tools and headless behavior of any real host are unproven. Never deploy it as enforcement without testing those properties with a real intercepted host side effect.

Direct portable policy validation does not rely on inherited `Array.prototype.every` or `includes`: a later same-process mutation of those helpers must not make an unexamined action, input field, or nested edit field pass. This is **not** a fix for the separate Pi executor's inherited `edits.map` after approval; frozen arrays remain vulnerable at execution and the prototype remains undeployable as a security boundary.

The Pi binder also requires the exact `event.input` object reference captured before approval; a matching clone must not be frozen instead of the arguments Pi will execute. Replacing that reference while approval is pending blocks even if its JSON content is identical. This only checks the reference the adapter supplies; it cannot authenticate that the adapter passed Pi's actual execution reference, nor prevent separate post-binding executor/prototype behavior.

The process-local permit and call-ID ledgers capture their collection operations when this module loads, so a later same-process change to `WeakSet.prototype.has` or `Set.prototype.has` cannot silently replay a consumed approval. Call-ID keys use length-prefixed string fields rather than serializing an array through a mutable inherited `toJSON`; separators within identity fields cannot collide. This does not authenticate host-supplied IDs, protect a compromised module loader or arbitrary code in the process, or repair Pi's separate inherited `edits.map` execution path.

The binder captures `Object.values` and `Object.freeze` at module load for nested detachment, freezing, and verification; replacing either static method after loading cannot silently leave executing nested edits mutable. This is not isolation from a compromised loader or arbitrary in-process code. The binder verifies object prototypes **after** freezing, with indexed traversal rather than mutable `Array.prototype.every`, so a nested Proxy that falsely reports successful detachment is rejected even after same-process prototype mutation. The in-memory call ledger also validates identity fields without `.every`. This does not neutralize mutable `Array.prototype` methods: even a frozen approved `edits` array can use a later-replaced `.map` during Pi edit execution. Until an adapter executes under a controlled realm or copies into an execution representation that does not inherit mutable methods, this prototype must not be deployed as a security boundary. A blocked binding can also leave a hostile Proxy's original input mutated; the adapter must never execute after a block.

## Pi v0.87.0 hook compatibility gate

Inspection of the installed `@earendil-works/pi-coding-agent@0.87.0` contract (`dist/core/extensions/types.d.ts:784–790,887–896` and `runner.js:852–867`) shows that `tool_call` receives a **mutable** `event.input`; later handlers see and can mutate it, and no re-validation happens after mutation. The hook result supports `block`/`reason`/`terminate`, **not replacement input or an approved-action permit**. `agent-session.js:245–256` passes the validated args reference to the runner; the nested `@earendil-works/pi-agent-core/dist/agent-loop.js:489–529,539–543` executes that same reference after the hook. Installed-Pi offline dispatch regressions (`tests/portable-pi-hook.test.ts`) exercise a registered file-writing tool and Pi's built-in `bash`, `write`, and `edit`: `tool_call` denial prevents each write; on approval, `bindPiExecutionInput` compares an adapter-supplied execution call envelope (host, session ID, call ID, cwd, task, tool, input) against the permit, then recursively freezes the original validated `event.input`. Tests reject changed call identity and flat or nested content; a later handler cannot mutate the frozen input before execution. The adapter must derive identity from authentic host state rather than copying the permit or trusting model-supplied fields. This is narrow Pi v0.87.0 ordering/argument-reference evidence, **not** production integration; remaining built-in tools, all effect-bearing tools, actual UI approval, bypasses, and extension ordering remain unverified. The prototype's detached frozen permit cannot simply be returned from a Pi `tool_call` handler and treated as binding to what executes: a later extension can change the original arguments after approval unless the original execution reference is also protected. Do **not** wire this seam into the existing Pi handler as an enforcement claim. A safe integration needs exclusive/wrapped execution of the permit snapshot, or a host guarantee that freezes and executes exactly the approved input after all handlers. Reverify on Pi version changes and test nested inputs, extension ordering, and actual approval before integration. The same sort of execution-contract audit is required for Hermes and Claude; ChatGPT remains unsupported.

## Verified Pi hook seam; not yet portable enforcement

The existing Pi extension registers `pi.on("tool_call", ...)` in `src/extension.ts`. Its deny path returns `{ block: true, reason }` before execution; its confirm path prompts through `ctx.ui.confirm` in dialog mode, while **advise mode lets ordinary confirm verdicts run**. Those are the existing Pi extension's semantics, not proof that `evaluatePortableAction` is wired into them. In particular, simply passing a portable `confirm` into the existing mode machinery would weaken this prototype's confirmation floor. An adapter must use a separate mandatory blocking path for portable decisions, fail closed without an interactive approver, and test a prevented side effect and refusal/reuse for the exact session, call ID, working directory, tool, and input. Do not represent a mocked `tool_call` invocation as proof of a real host interception guarantee.

## Claude Code hook feasibility (documentation only)

The [official Claude Code hooks reference](https://code.claude.com/docs/en/hooks#pretooluse) defines `PreToolUse` JSON with `session_id`, `cwd`, `tool_name`, `tool_input`, and `tool_use_id`; a matching hook can return `hookSpecificOutput.permissionDecision` of `deny`, `ask`, `allow`, or `defer`. `deny` blocks a covered call; `ask` invokes Claude's own permission prompt, **not** a verified pi-warden approval bound to a canonical action snapshot. `updatedInput` replaces the entire tool input and is permission-checked again, but a portable adapter must still prove what finally executes. `Bash`, Windows `PowerShell`, `Write`, and `Edit` have distinct schemas; MCP tools require their own coverage. `PreToolUse` is not a universal file-access interceptor: prompt `@` references do not call `Read` and `EndConversation` skips the hook.

A command, HTTP, or MCP `PreToolUse` hook that times out produces **no blocking decision** and proceeds through normal permissions; an Agent SDK callback timeout blocks instead. Other nonzero exit statuses also need an explicit valid decision or the documented blocking exit-2 path. Therefore a standalone CLI hook is not fail-closed merely because its policy evaluator intends to deny on error. Matched handlers run in parallel, and interactive workspace trust can suppress settings hooks pending acceptance. No Claude integration is installed here. Before any enforcement claim, test the actual installed Claude version with deny, ask/decline, timeout, malformed output, parallel hooks, permission modes, background shell actions, and all mapped tool shapes; ensure a trusted host owns approval/session identity and a failed policy process cannot fall through to an effectful permission grant. Hosted ChatGPT is a separate surface with no verified hook contract.

## Hermes hook feasibility (documentation only)

The [official Hermes Event Hooks reference](https://hermes-agent.nousresearch.com/docs/user-guide/features/hooks#pre_tool_call) specifies a `pre_tool_call` directive hook for built-in and plugin tools in CLI and gateway sessions. A Python plugin receives `tool_name`, raw `args`, `task_id`, and correlation fields (`session_id`, `tool_call_id`, `turn_id`, `api_request_id`); `block` vetoes and `approve` invokes the existing human-approval gate, where decline, timeout, or error blocks. A Python callback exception or timeout also blocks for this **specific** policy hook. Unlike Claude Code's command hook, a Hermes shell `pre_tool_call` hook defaults to fail-open on spawn error, malformed output, or timeout: security use requires explicit `fail_closed: true`. An outbound webhook is notify-only, and a gateway event hook is not a CLI tool interceptor. None is installed by this prototype.

Hermes also accepts `modify` directives that shallow-merge tool arguments; multiple hooks may modify the same call. A portable adapter must prove the approval snapshot matches the **final arguments executed**, including edits from other hooks and all effect-bearing tool fields, rather than assume seeing the initial `args` is enough. Hook payload IDs are opaque and can be absent; do not manufacture an authenticated approval context from missing IDs or model-supplied task text. The present mapper only covers three named Hermes tool shapes, not all tools (including delegated/compound tools). Before enabling it, use an isolated Hermes profile to verify real block/approve/decline, missing-identity, timeout/error, `modify` ordering, coverage, and external side-effect prevention without changing this running agent's hooks or approval rules. A valid hook registration is not evidence of full host enforcement.

## ChatGPT MCP server boundary (documentation only)

The [OpenAI plugin MCP server guide](https://developers.openai.com/plugins/build/mcp-server) puts input validation, authorization, and consequential-write confirmation **inside the server**; `readOnlyHint`, `destructiveHint`, and `openWorldHint` are host-facing hints, not server-side controls. A pi-warden wrapper around a server's own effectful MCP handlers could evaluate their parsed arguments before the server performs the effect, then reject on deny, policy failure, unavailable approval, or changed arguments. This protects only those wrapped handlers; it does **not** intercept ChatGPT's built-in tools, other MCP servers, Codex CLI tools, or arbitrary local shell/file operations. A tool result or widget notification is too late to block a side effect. No MCP adapter is implemented or installed here.

The [OpenAI plugin reference](https://developers.openai.com/plugins/reference) describes `_meta["openai/session"]` as an anonymized conversation identifier and `_meta["openai/subject"]` as an anonymized user identifier provided on tool calls. These are correlation inputs, not independently verified authorization or action-scoped approval; optional user-agent/location metadata are hints and must not authorize anything. A real server must enforce its own authenticated principal and resource permissions, identify the exact tool call and approved arguments, reject replay or changed arguments, and establish a trusted approval/decline path before executing. ChatGPT's own confirmation UX must not be assumed to produce a pi-warden-bound approval. Test with the actual ChatGPT client and server using an observable prevented write, malformed/missing metadata, denied authorization, decline/headless timeout, argument changes, repeated calls, and tools outside the wrapper. Hosted ChatGPT is **not** a verified general pre-tool hook for this prototype.

Next before deployment: implement and test each host's actual hook contract, prove the hook can block a real side effect, map all effect-bearing tools without losing arguments, bind approvals to the originating request and action, and calibrate false holds against real trace data. Do not install this prototype as a blanket extension or treat the named hosts in tests as working integrations.
