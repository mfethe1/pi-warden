# Portable action boundary (experimental)

`src/portable-action.ts` is a host-neutral **pre-execution policy core**, not an installed Hermes, Claude, ChatGPT, or Pi integration. Adapters must capture the actual tool invocation before execution, pass the current user's task (not agent text or retrieved content), and enforce `deny` by blocking and `confirm` by obtaining fresh, action-scoped user approval. A host that cannot intercept before execution must not claim enforcement. No approval persistence or cross-session carryover is provided here.

The core maps specific host/tool pairs: Pi (`bash`, `write`, `edit`), Hermes (`functions.terminal`, `functions.write_file`, simple `functions.patch` replace), and Claude (`Bash`, `Write`, `Edit`). These are *input-shape fixtures*, not verified hook integrations. ChatGPT has no verified hook contract and is denied until one is implemented. Cross-host tool aliases, mismatched working directories, unknown hosts/tools, unknown action-envelope fields, unexpected tool options (including background execution and timeouts), unknown nested edit fields, malformed `replace_all` values, unsupported arbitrary-code tools, bulk edits beyond the guard's sample limit, and patch-format edits fail closed rather than being guessed read-only. It never silently allows a mapped shell, write, or edit call: because shell semantics and symlink targets are not verified, even a guard `allow`/`warn` is raised to `confirm` pending action-scoped approval; an existing `deny` stays denied. This conservative default is intentionally high-friction until real host adapters and approval binding are proved. It neither connects a judge nor transmits data. The `verdict` object contains a summary and is intended for local inspection, not automatic telemetry.

## Experimental preflight seam (not wired to a host)

`preflightPortableAction` in `src/portable-preflight.ts` converts the decision into a `{ block: true, reason }` response or `{ block: false, action }` permit only after a fresh, explicit `true` from an injected approver. The policy, approver, and compliant executor must use the **same deeply frozen action snapshot returned in the permit**; the original mutable request is not authorized for execution. `executePortableAction` is an opt-in callback wrapper that passes only that approved snapshot to its executor and skips the callback for blocked requests; tool failures propagate rather than being mislabeled as pre-execution blocks. No approver, decline, approval exception, policy denial, non-JSON action, or mutation while approval is pending blocks. An in-process test proves that the wrapper skips a real local file write for declined/headless/changed requests and writes the approved snapshot despite a later original-request mutation. This does **not** prove any real host intercepts tool calls or prevents bypass of the wrapper. A host may supply a shared `PortableCallLedger` to consume `(host, sessionId, callId)` synchronously before awaiting approval; concurrent or later reuse (including after a decline) is blocked. This is opt-in, process-local replay resistance only: restarting the host resets the ledger, a new call ID is distinct, and the host must ensure session/call IDs are authentic and unique. It does not prove a reused approver callback actually solicits a fresh human decision. No durable approval token or production hook is provided. Rebinding the **same permit object** through the experimental Pi binder is now rejected, but a copied permit or a newly approved permit is not covered by that process-local identity check; the optional shared ledger remains necessary to reject repeated call IDs at preflight. Inherited prototype properties also remain a known gap: a polluted `Object.prototype` can change what an approved frozen object resolves during execution. Do not rely on this binder where untrusted code can mutate shared prototypes; execution must use a canonical, own-data-only action and an authenticated host call identity. The calling host must route *every relevant tool execution* through the wrapper (or enforce the block and execute the permit snapshot), before any other guard bypass. Unhooked tools and headless behavior of any real host are unproven. Never deploy it as enforcement without testing those properties with a real intercepted host side effect.

## Pi v0.87.0 hook compatibility gate

Inspection of the installed `@earendil-works/pi-coding-agent@0.87.0` contract (`dist/core/extensions/types.d.ts:784–790,887–896` and `runner.js:852–867`) shows that `tool_call` receives a **mutable** `event.input`; later handlers see and can mutate it, and no re-validation happens after mutation. The hook result supports `block`/`reason`/`terminate`, **not replacement input or an approved-action permit**. `agent-session.js:245–256` passes the validated args reference to the runner; the nested `@earendil-works/pi-agent-core/dist/agent-loop.js:489–529,539–543` executes that same reference after the hook. Installed-Pi offline dispatch regressions (`tests/portable-pi-hook.test.ts`) exercise a registered file-writing tool and Pi's built-in `bash`, `write`, and `edit`: `tool_call` denial prevents each write; on approval, `bindPiExecutionInput` compares an adapter-supplied execution call envelope (host, session ID, call ID, cwd, task, tool, input) against the permit, then recursively freezes the original validated `event.input`. Tests reject changed call identity and flat or nested content; a later handler cannot mutate the frozen input before execution. The adapter must derive identity from authentic host state rather than copying the permit or trusting model-supplied fields. This is narrow Pi v0.87.0 ordering/argument-reference evidence, **not** production integration; remaining built-in tools, all effect-bearing tools, actual UI approval, bypasses, and extension ordering remain unverified. The prototype's detached frozen permit cannot simply be returned from a Pi `tool_call` handler and treated as binding to what executes: a later extension can change the original arguments after approval unless the original execution reference is also protected. Do **not** wire this seam into the existing Pi handler as an enforcement claim. A safe integration needs exclusive/wrapped execution of the permit snapshot, or a host guarantee that freezes and executes exactly the approved input after all handlers. Reverify on Pi version changes and test nested inputs, extension ordering, and actual approval before integration. The same sort of execution-contract audit is required for Hermes and Claude; ChatGPT remains unsupported.

## Verified Pi hook seam; not yet portable enforcement

The existing Pi extension registers `pi.on("tool_call", ...)` in `src/extension.ts`. Its deny path returns `{ block: true, reason }` before execution; its confirm path prompts through `ctx.ui.confirm` in dialog mode, while **advise mode lets ordinary confirm verdicts run**. Those are the existing Pi extension's semantics, not proof that `evaluatePortableAction` is wired into them. In particular, simply passing a portable `confirm` into the existing mode machinery would weaken this prototype's confirmation floor. An adapter must use a separate mandatory blocking path for portable decisions, fail closed without an interactive approver, and test a prevented side effect and refusal/reuse for the exact session, call ID, working directory, tool, and input. Do not represent a mocked `tool_call` invocation as proof of a real host interception guarantee.

Next before deployment: implement and test each host's actual hook contract, prove the hook can block a real side effect, map all effect-bearing tools without losing arguments, bind approvals to the originating request and action, and calibrate false holds against real trace data. Do not install this prototype as a blanket extension or treat the named hosts in tests as working integrations.
